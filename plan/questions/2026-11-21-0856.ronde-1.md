### Q1/5 [method] : Re-measure what the others already measured

tzimpel (#28) measured most of the Swoole tuning with exactly our method: CPU µs/req at a fixed rate, variants
interleaved. 2 workers cost 27 % more CPU, the background checkpointer takes the p99 from 43 to 4 ms, PDO beats the
`SQLite3` extension, JSON in PHP beats JSON in SQLite. Re-measuring all of it costs days. Taking it as given skips the
part where you see each step behave with your own eyes, which is part of why you want this plan (D3).

**In short:** prior art answers half of the step lab already; the question is whether we trust it or redo it.

**Question:** for a result another submission already measured, do we re-measure it ourselves?

- **A.** Only when it's cheap or when it decides something big (the connection ceiling, the checkpointer, the feed
  query). The rest we take as given, with the source noted next to the step.
  **Aims at:** a faster path to a score above 71,000.
  **For:** days saved on things with a known answer. **Against:** you won't have seen those steps behave yourself.
- **B.** Re-measure everything, prior art only tells us what to expect.
  **Aims at:** understanding each step from our own numbers (D3).
  **For:** our numbers on our setup, and their numbers become predictions we can check. **Against:** a lot of time
  on results that are probably the same; their hosts drifted by 10 %, so will ours.

**Confidence:** A 55 % · B 45 %

**Recommendation:** A: I put getting past 71,000 before redoing known results, but it's a close call. Your learning
goal could easily win.

**Flips if:** understanding every step matters more to you than the score itself.

**Answer:** B, let's "think again"and not asume they were right, even if my feeling is they probably were. I want to challenge every thing, and understand every steps

### Q2/5 [runtime] : Which runtimes go into the bake-off

Theory in [details/runtimes.md](details/runtimes.md). The bake-off runs the same minimal handler on each and measures
µs/req, max connections and RSS per connection. Each runtime costs about half a day to set up and measure.

**Question:** which of these runtimes do we measure in the bake-off?

1. **Swoole 6.2.** **Aims at:** the known best. **For:** C parser and loop, 71,000 already reached, prior art to
   build on. **Against:** none for a baseline.
2. **Workerman 5.** **Aims at:** a pure-PHP stack we fully control. **For:** the only serious PHP-userland
   competitor; it shows what a PHP parser costs against Swoole's C one. **Against:** its parse cache may break rule 5,
   and it does more PHP per request on paper.
3. **DIY loop and parser** (ext-event, raw sockets). **Aims at:** the least possible work per request. **For:** we
   parse only what 5 routes need, and it teaches the most. **Against:** the most code, and it must beat C parsing
   with PHP parsing.
4. **RoadRunner.** **Aims at:** a modern Go front. **For:** Go handles connections well. **Against:** two IPC hops
   per request on one core, and one process, so the same fd ceiling.
5. **FrankenPHP worker mode.** **Aims at:** a modern Go front without IPC. **For:** PHP embedded in-process.
   **Against:** cgo crossings, Caddy middleware, a slower ZTS PHP, one process.
6. **OpenSwoole.** **Aims at:** a Swoole alternative. **For:** same design. **Against:** an older fork, nothing it
   does better on paper.

**Confidence:** 1. 95 % · 2. 60 % · 3. 45 % · 4. 20 % · 5. 20 % · 6. 10 %

**Recommendation:** 1 and 2 for sure, 3 is a close call. 4, 5 and 6 cost a day for an answer the theory already
gives.

**Flips if:** 3. if Workerman's PHP parser lands within 10 % of Swoole · 4. and 5. if you want the comparison
written down for its own sake (a blog post, say) · 6. if Swoole fails to build on the VM.

**Answer:** 1, 2, 3, but for 2, make sure it doesn't break the rule 5 to avoid loosing time.

### Q3/5 [measure] : Where we measure

The Mac is an Apple M3 Pro (arm64); the bench VM is an x86_64 Xeon. The others saw their local machine 1.8x to 3.2x
faster than the VM. Relative results (variant A against B) should hold; absolute numbers (users, µs/req) don't.
Testing 65k+ connections also needs a load generator that can hold them: mattsplat's k6 container ran out of memory at
22,000 users.

**Question:** where do we run the measurements?

- **A.** In a Docker container on the Mac (Ubuntu 24.04, `--cpus=1 --memory=2g`), k6 on the Mac. A $12 x86 VPS only
  for the final runs, to calibrate the ratio.
  **Aims at:** fast iterations, nothing to pay or manage.
  **For:** a variant takes minutes to compare. **Against:** arm64, and the network path differs from the VM's.
- **B.** A $12 x86 VPS (1 vCPU, 2 GB) from the start, with a second VPS as load generator.
  **Aims at:** numbers that compare with the leaderboard directly.
  **For:** same architecture as the bench. **Against:** about $25 a month, slower iterations, and noisy neighbours.

**Confidence:** A 70 % · B 30 %

**Recommendation:** A: I put iteration speed first, since most of the step lab compares variants with each other.

**Flips if:** a variant's ranking on the Mac turns out different on x86 (we'd see it at the first calibration).

**Answer:** A, and if needed we'll go to B for testing. Does AWS have a Xeon to test? Could we test with another server just beside it, like having 2 EC2 in the same region to test directly?

### Q4/5 [php] : Which PHP build

Ubuntu 24.04's apt gives PHP 8.3.6, what both Swoole entries used. PHP 8.4 or 8.5 means compiling it in `install.sh`
(several minutes on 1 vCPU, and one submission failed on an install timeout). tzimpel found the JIT roughly neutral,
since most of the time is spent in C.

**Question:** which PHP do we start with?

- **A.** apt's PHP 8.3, and a PHP 8.5 build as one variant in the step lab.
  **Aims at:** the same baseline as the prior art.
  **For:** nothing to compile, our numbers compare with theirs. **Against:** we might leave a newer engine's gain on
  the table until we measure it.
- **B.** PHP 8.5 compiled from source from day one.
  **Aims at:** the newest engine.
  **For:** any engine gain is in every measurement. **Against:** longer install, and no direct comparison with the
  prior art.

**Confidence:** A 75 % · B 25 %

**Recommendation:** A: I put a baseline comparable with the prior art first.

**Flips if:** a quick micro bench shows PHP 8.5 more than 10 % faster on our handler code.

**Answer:** I'm not sure, could we test on each php versions (each means 8.3, 8.4, 8.5, 8.6)? Also, note that PHP 8.6.0 was released on November 19, 2026

### Q5/5 [uml] : Diagram format

The UML sequences are drafted in [details/sequences.md](details/sequences.md), in Mermaid.

**Question:** do we keep the diagrams in Mermaid?

**Confidence:** A 85 % · B 15 %

**Recommendation:** A: I put diagrams that are easy to keep up to date first.

**Flips if:** the Mermaid preview doesn't render in your PhpStorm.

**Answer:** A
