## 🟠 MAJOR (should be fixed)

### 1. "Memory under load, Pss" counts the database pages SQLite maps, so it compares request counts, not runtimes

`lab/servers/handler.php:52`, `lab/macro/probe.sh:42-53` (`memory-now`), `lab/README.md:274` and `:421` ·
**Certainty:** plausible (mechanism read in the code and measured on the seed, not run under k6)

- **Why:** the handler sets `PRAGMA mmap_size = 268435456`, so SQLite reads the 250 MB copy through a memory mapping.
  Every page a request touches becomes resident in the server's own mapping. `Pss` from `smaps_rollup` counts
  file-backed mapped pages too, and only one process maps the file, so each page counts in full. The README says the
  opposite: "use the Pss reading below to compare runtimes", "it is what the server costs".
- **Scenario:** in the seed, `posts` is 21,077 pages (82 MiB), `likes_post_id_idx` 5,913 pages (23 MiB) and `users` 639
  pages. `posts.js` spreads its ids over the whole table, and the warm-up replays the same ids. Run Swoole at 7,000 req/s
  (10 s warm-up, so 70,000 requests) and DIY at 3,000 req/s (30,000 requests). The first run has touched about 96 % of
  those pages before the measured run starts, the second about 76 %. The Pss gap is about 20 MiB of database pages,
  while the runtimes themselves differ by a few MiB. The `/posts` checks only assert `max_pss_mib > 0`, so nothing
  catches it.
- **Flips if:** every memory comparison is made at the same rate, duration and warm-up (then the database part is about
  equal), or the Docker VM's SQLite build ignores `mmap_size` (it doesn't by default on 64-bit Linux). Worth checking:
  the Pss of a `/noop` run against a `/posts` run on the same server.
- **Fix:** in `probe.sh memory-now`, also sum `Pss_Anon` (in `smaps_rollup` since Linux 5.x), record it in
  `results.memory.under_load` and in the table, and have the README compare runtimes on it. Keep the full Pss next to it,
  as "including the mapped database". Check to add: on the same server, `/posts` `Pss_Anon` stays within a few MiB of
  `/noop`.

## 🟡 MINOR (suggestion)

2. `lab/README.md:384`: "Every measuring script of the lab does the same" (recording other containers). `lab/micro.sh`
   doesn't, and it is the most noise-sensitive script (`README.md:210-213` already describes a busy VM changing micro
   numbers). Either add `other_containers` to `micro.sh`, or narrow the sentence to `macro.sh` and `conns.sh`.
3. `lab/conformance.sh:10`: "two pipelined requests", but the `pipelining` case sends three (`client.php:198`, and the
   README says three).
4. `lab/README.md:103`: "Workerman keeps an HTTP connection alive for 60 s". I find no idle timer in Workerman 5.2.4's
   `TcpConnection` or `Http`. The 60 s looks like PHP's `default_socket_timeout` on the client side, and Workerman keeps
   the connection open indefinitely. That matters to `conns.sh`, which relies on no idle close. Plausible: rerun the trap
   with `default_socket_timeout=5` to tell the two apart.
5. `lab/images/install-extras.sh:25`: "its version is whatever the pinned Ubuntu digest ships" is not right: `apt-get
   update` pulls the archive as it is on build day, so `libevent-dev` can move between two builds of the same digest.
   `php-info` doesn't print it either. Print the libevent version (`dpkg-query -W libevent-dev`) in `php-info`, or fix the
   comment.
6. `lab/servers/diy-connection.php:141-142`: no `try` around `handler_handle()`, and `HEAD` only knows 200, 400 and 404.
   A PDO exception (`SQLITE_BUSY` after the 5 s `busy_timeout`, for example) escapes the ext-event callback and stops the
   DIY loop for every connection. Workerman catches it and keeps serving (`TcpConnection` calls `error()`), so the
   runtimes would fail differently on the same fault. The spec wants `500 {"error":"internal server error"}`.
7. `lab/servers/diy-connection.php:183-187`: `Content-Length : 5` (a space before the colon) is read as an unknown
   header, so the body is parsed as the next request. RFC 9112 §5.1 says to answer 400. It is the same smuggling concern
   as the comment on line 189: reject any header name that ends in a space or a tab.
8. `lab/servers/diy-connection.php:39`: "so a request allocates nothing", and `README.md:315` "nothing is allocated per
   request but the strings": `explode()` builds an array of header lines on every request (line 182). In a bake-off about
   per-request cost, write what is actually allocated, or scan the headers with `strpos` instead.
9. `lab/check.sh:49`: "The phase-2 lines are checked by check_source_image" only means something to someone who has read
   the plan. Name them instead: "the PHP, OPcache, SQLite and Swoole lines".
10. `lab/servers/workerman-caches.php`: a check living next to the servers. The two DIY tests live in `lab/check/`, and
    this file belongs there too.
