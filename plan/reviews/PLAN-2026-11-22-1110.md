## 🔴 CRITICAL

1. **With 60,000 idle connections held, k6 gets at most about 500 ephemeral ports for up to 3,000 VUs.**
   - **The mechanism:** the idle client calls `bind(127.0.0.x:0)` before each connect (`lab/conns/client.php:133`, `:168`). On Linux, a port reserved by `bind()` is skipped by `connect()`'s automatic port choice on every address (`__inet_hash_connect` skips any bind bucket with `fastreuse >= 0`). k6 connects from 127.0.0.1 without binding (`lab/macro.sh:185`).
   - **The arithmetic:** the client binds 10,036 ports per address on 6 addresses, which covers the whole 55000-65535 range except its 500-port margin.
   - **What fails:** k6's VUs fail with `cannot assign requested address`.
   - **Why no scope catches it:** scope 3's Done-when uses `--idle 5000`, which leaves k6 5,536 ports, so it passes without the D36 sizes ever being run. The first full-size run is in scope 5, on the quiet VM (`details/phase-4.md:40`, `:136-140`, `:186`).

## 🟠 MAJOR

2. **The VU budget doesn't close.**
   - **The scale can't reach the predicted knee:** the default scale puts 9,500 req/s at 2,500 VUs (`details/phase-4.md:119-120`). The 3,000-VU cap then offers at most 11,400 req/s, while prediction 3 says the knee is 10,000 to 18,000 (`:220`). The coarse staircase's 12,000 step needs 3,158 VUs and is refused (exit 2). The staircase has no failing step, so the run has no baseline.
   - **D36's rule is circular:** "knee at most 2,500 VUs" can't be picked at a calibration of 50 VUs (`decisions.md:113`).
   - **The memory budget doesn't close either:** prediction 12's 2 MiB per VU × 3,000 VUs is 5.9 GiB. Add the server's 2 GiB limit and the VM's 7.75 GiB is exceeded (`:239-241`). k6's own guide says 1 to 5 MB per VU (`notes.md:283`).
   - **An overrun has no clean failure:** the k6 container has no memory limit (`lab/macro.sh:181`). An overrun becomes VM swapping (host stalls, which Q10 would read as stalls) or an OOM kill. No fallback is written.
3. **10.8 users per req/s is a whole-run ratio, not a plateau ratio.**
   - **Where it comes from:** k6's `http_reqs` rate on the leaderboard includes the 60 s ramp-up and the 30 s ramp-down (about 10.7 in theory, 10.2 to 10.84 observed). A plateau's ratio is 20.5 / 2.17 = 9.45 users per req/s.
   - **The effect:** mapped users are inflated by about 14 %. D16's "7,000 req/s = 75,000 users" is about 66,000, and 9,500 req/s is about 90,000. 🤝's "9.2 million / µs" is about 8.0 million.
   - **Where it's used:** `decisions.md:94-99`, `:43`, `plan.md:29-30`, `details/measuring.md:20`, `:38`.
4. **Nothing says how one k6 run yields per-step and per-second numbers, and the obvious route disturbs the measurement.**
   - **The summary can't do it:** k6's end-of-test summary has no per-step or per-second breakdown (`details/phase-4.md:122-125`, `:141-144`, "the developer's call").
   - **Raw samples are heavy:** k6 emits about 12 metric rows per request. At 15,000 req/s, a 5-minute hold is about 54 million rows, several GB, written to the VM disk that the server's checkpoint `fsync`s also use, and paid in k6 CPU.
   - **What that breaks:** the lab can create the very stalls Q10 is looking for, and eat the 97 % rule's margin.
5. **Q10's runs need `macro.sh` to run the skeleton warm and cold, and no scope builds it.**
   - **What's missing:** `macro.sh` starts the server through `lab_start_server` (`lib.sh:85-92`): no fresh writable copy, no `SQLITE_PATH` (D32), no `--cold`.
   - **Where the scopes fall short:** scope 3 gives `--cold` to `realistic.sh` only (`details/phase-4.md:134`, `:151-155`). Scope 5 (measurement only) needs `posts.js` on the skeleton, 3 warm and 3 cold (`:195-198`).
6. **Nothing proves that Excimer's samples land on the internal function's frame under the tracing JIT.**
   - **How Excimer samples:** at the next VM interrupt check, and its docs say time in a C function is "attributed to the caller".
   - **What happens if the frame is missing:** if `PDOStatement::execute`, `json_encode` or `fwrite` isn't on the sampled stack, S6, S7 and S8 time lands on the route function. That's S3, or unclassified, and the "under 5 % unclassified" Done-when can still pass with broad rules.
   - **What the cases miss:** they test the fold's arithmetic and that every endpoint is present (`details/phase-4.md:166-177`), not where the samples land. Phase 5's order depends on it (`:200-201`).

Read `mxFrame` from the `-shm` header (offset 16) from the probe instead (`details/phase-4.md:143`, `:146`, `:228-229`).

### [run, lab] : Free k6's ports when 60,000 idle connections are held

The idle client's `bind(127.0.0.x:0)` reserves ports that `connect()` then skips on every address. With 60,000 held, it
covers the VM's whole 55000-65535 range except about 500 ports, and k6 (from 127.0.0.1, no bind) needs up to 3,000
(item 1). A `bind()` with an explicit address only conflicts on the same address, so k6 bound to its own addresses
shares the port numbers with no trouble.

**Question:** how do the idle client and k6 share the ports?

- **A.** k6 binds its own source addresses with `--local-ips` (for example 127.0.1.1 to 127.0.1.4), set by `realistic.sh`.
  **Aims at:** the smallest change, k6-native, nothing VM-wide.
  **For:** one option in the harness, and the client stays as phase 3 tested it. **Against:** k6's connections no longer come from 127.0.0.1, so the JSON must record it.
- **B.** The idle client sets `IP_BIND_ADDRESS_NO_PORT` (through ext-sockets), so the kernel picks the port at `connect()` per 4-tuple.
  **Aims at:** same goal, fixed at the source, so any client added later also works.
  **For:** the reservation disappears. **Against:** the client moves from PHP streams to `socket_*` calls, more code in a file `conns.sh` shares.
- **C.** Widen `ip_local_port_range` in the VM.
  **Aims at:** same goal, without touching the code.
  **For:** no code change. **Against:** a VM-wide change, which the lab avoids (D33's rule for `perf`), and it hides the problem.

**Confidence:** A 65 % · B 30 % · C 5 %

**Recommendation:** A: it keeps the measurement unchanged at the lowest cost, and adding `--idle 60000` with the VU cap
to scope 3's Done-when proves the fix before scope 5.

**Flips if:** k6 1.8.3's `--local-ips` fails on loopback addresses (then B).

### [run, lab] : Size the VU cap and the think scale from measurements

**See also:** the users mapping question

At the default scale (9,500 req/s at 2,500 VUs), the 3,000-VU cap offers at most 11,400 req/s, while the predicted knee
is 10,000 to 18,000. k6's memory per VU is unknown (the guide says 1 to 5 MB), and 3,000 × 2 MiB plus the server's
2 GiB already exceeds the 7.75 GiB VM (item 2). A lower scale needs fewer VUs, but shrinks the 97 % rule's latency
margin (about `0.29 × s` seconds mean per request).

**Question:** how are the cap and the scale picked?

- **A.** In calibration: measure k6's MiB per VU, set the cap to (VM memory − 2 GiB server − idle client − 1 GiB margin) / that value, then pick `s` so that 20,000 req/s fits under the cap.   **Aims at:** a staircase that can always reach a failing step, and no VM-wide memory pressure.

- **B.** Keep the default scale and cap, and lower `s` by hand if the staircase reaches the cap without a failing step.
  **Aims at:** the least change to the plan.
  **For:** nothing to build. **Against:** the failure shows up in scope 5, on the quiet VM, and costs a rerun.

**Confidence:** A 80 % · B 20 %

**Recommendation:** A: a reachable knee matters more than a looser margin, and the margin is recorded so phase 5 can
read it.

**Flips if:** calibration shows k6 under 1 MiB per VU, so 5,000+ VUs fit (then raise the cap instead of lowering `s`).

### [run, lab] : Get per-step and per-second numbers out of k6 without disturbing the run

several GB per 5-minute hold, written to the disk that the server's checkpoints `fsync` (item 4).

**Question:** how does the harness get per-step and per-second latency?

- **A.** Per step: one k6 scenario per step (built by the harness in `options`, so the script's diff stays "options only"), with thresholds on the `{scenario:…}` and `{scenario:…,name:…}` submetrics.   **Aims at:** the simplest code.
  **For:** everything is kept. **Against:** disk and CPU on the measured VM, which is exactly what Q10 must rule out.
