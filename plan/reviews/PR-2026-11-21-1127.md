## PR description (draft, English, final branch)

**Summary**

Phase 2 of the plan: a measuring lab under `lab/` that builds the same data and the same environment for every measurement, and a first number from it: what a no-op Swoole server costs per request at a fixed rate.

```diff
 lab/
+  seed.sh                  seed database, outside git
+  build.sh, run.sh         php-lab:8.3-apt, 8.3, 8.4, 8.5, 8.6 (Ubuntu 24.04), 1 CPU, 2 GiB
+  micro.sh, micro/         micro benchmarks, JIT on and off, K processes per case
+  macro.sh, macro/         k6 at a fixed rate, CPU read from the cgroup
+  servers/noop-swoole.php  the floor: 200 {"status":"ok"} to everything
+  check.sh                 15 smoke checks
+  results/                 build times, the Swoole-on-8.6 failure, the first number
```

**Decisions**

- **8.3 is built from source as well as from apt:** otherwise "8.4 is faster than 8.3" could just mean "our build flags beat Ubuntu's". For the same reason every lab PHP run pins `zend.assertions=-1` and `opcache.file_update_protection=0`, so the source images (no `php.ini`) behave like Ubuntu's.
- **Swoole does not build on PHP 8.6:** the 8.6 image has no Swoole, so only the micro benches run on it; the error is saved.
- **The micro harness runs each case in 5 processes and reports the spread across them:** the same case swung 2x from one process to the next on this Mac, and a spread inside one process hid it.
- **k6 runs in its own container on the VM's host network, and the CPU is read from a third container:** a port forwarded from macOS goes through a userspace proxy, and a read inside the server's cgroup would be part of the number.
- **The default port is 18080:** 8080 and 80 are taken by other containers on the VM's host network.

**Changes**

- Seed script, image builds pinned by sha256 and digest, build times recorded.
- Micro harness: check before timing, JIT state verified, spread across processes, UNSTABLE flag.
- Macro harness: fixed-rate k6, valid/invalid runs, connections, memory, k6 CPU, the ini values the server ran with.
- `lab/check.sh`: 15 checks, green.
- First number: 9 interleaved runs, prediction written before.
- README: prerequisites (Docker Desktop, Node 18 or later, `sqlite3`, `jq`), a link from the root README.

**Proof**

`bash lab/check.sh` prints 15 `ok`. The first number, on an Apple M3 Pro in Docker Desktop (arm64, not the bench VM), image `8.3-apt`: **50.2 µs/req at 1,000 req/s, 30.2 at 3,000 and 21.7 at 6,000**, all 9 runs valid (0 errors, 0 dropped iterations). The prediction of 8 to 20 µs at 3,000 did not hold; the trend (cheaper per request at a higher rate) did, and peak RSS stayed under 50 MB. The rate and the connection count rise together in this series, so the "fixed cost per second" is not yet attributed. To check it yourself: `bash lab/seed.sh && bash lab/build.sh 8.3-apt && bash lab/macro.sh --image 8.3-apt --server lab/servers/noop-swoole.php --rate 3000 --duration 30`, and compare with `lab/results/2026-11-21-noop-swoole/`.

**Merge risk**

- **Door:** two-way. New files only; nothing existing is changed except `.gitignore` and the root README.
- **Blast radius:** none outside `lab/`. The numbers are arm64, on a Mac that was not quiet; they are relative, not the score.

**Implementation choices**

- `lab/macro.sh` runs k6 with `docker exec` in a long-lived container so its cgroup still exists when its CPU is read.
- Open connections equal the VUs k6 pre-allocated (k6 rotates iterations over all idle VUs), so the default is rate/10 VUs, started before the test.

**Left for a later pass**

- `lab/macro.sh` reports a k6 that dies at once only after three quarters of the run.
- The Swoole version and sha256 are written in two install scripts (the apt one doubles as a standalone `install.sh`) and `lab/check.sh` hardcodes `6.2.6`.
