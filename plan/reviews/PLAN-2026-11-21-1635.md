## 🟠 MAJOR

2. **The connection test's ceiling depends on each server's listen backlog, which nobody sets.** Swoole's no-op
   server sets 4,096 (`lab/servers/noop-swoole.php:26`), Workerman asks 102,400 (clamped to 4,096), and a DIY server
   on `stream_socket_server` gets PHP's default of 32 unless it passes `socket.backlog`. With
   `tcp_abort_on_overflow` 0, a burst that overflows the accept queue drops the handshake's last ACK silently: the
   client's request waits for retransmits (1 s, then 3 s), and the plan's 1 s rule calls it a ceiling. Scenario: DIY
   at the 1k step, 1,000 connects in a tight loop, a queue of 32: "ceiling: timeout at 1,000" for a server that holds
   65k. The plan also says nothing about how fast the client opens connections.
3. **The max and the stop reason, as written, can be wrong.** (a) Linux never answers a SYN with "refused" because the
   accept queue is full or the server is out of fds: the connection completes in the kernel, then times out (EMFILE,
   queue full) or is reset (Swoole closing past `max_connection`). Scope 3's case "ceiling under 2,048 with reason
   refused or reset" can fail on a correct harness, and pushes the developer to bend the classifier. (b) Connections
   waiting in the accept queue are `ESTABLISHED` in `/proc/net/tcp`, so "the exact count of connections still
   established" overcounts at the fd wall: at the 66k step, Workerman or DIY holds about 65,520 but the count reads
   about 66,000. (c) Client-side errors aren't separated from server ceilings: scope 7 runs `conns.sh` back to back,
   and a 66k run that the client closes leaves 66k `TIME_WAIT` sockets on 127.0.0.2 to .4 for 60 s; the next run's
   `bind()` fails with "address in use", which reads as "refused" for the second runtime.
4. **The partial-write case doesn't force a partial write.** Reading 1 KiB at a time on the client doesn't shrink any
   kernel buffer; on loopback the send and receive buffers autotune to megabytes, and a `/posts/:id` response is under
   1 KiB. PHP streams can't set `SO_RCVBUF` (no `ext-sockets`). Scope 6's Done-when ("large-response cases included")
   goes green while DIY's partial-write path never runs, and that path is the riskiest code of the scope.

### [run, conns] : Which number is "max connections" in the table?

**Depends on:** the backlog question above

Three facts the plan doesn't account for. Linux never refuses a SYN because of the accept queue or the server's fd
limit: the connection completes, then times out or is reset, so scope 3's case "reason refused or reset" can fail on a
correct harness. Connections waiting in the accept queue are `ESTABLISHED` in `/proc/net/tcp`, so that count reads
about 66,000 when Workerman or DIY holds about 65,520. And a 66k run the client closes leaves 66k `TIME_WAIT` sockets
on 127.0.0.2 to .4 for 60 s: scope 7's next `conns.sh` can't bind, which looks like a server ceiling.

**In short:** count from the client, and keep the client's own errors out of the ceiling.

**Question:** where does the max come from, and how are the stop reasons classified?

- **A.** The max is the number of connections that got their answer and are still open, counted by the client;
  `/proc/net/tcp` stays in the JSON as a cross-check. Reasons: timeout, reset, closed, fresh request failed, OOM.
  A client-side error (`bind`, `EMFILE`, no port) exits non-zero as a harness failure, and a run waits until no
  `TIME_WAIT` socket remains on its source addresses (or uses its own block of 127.x addresses).
  **Aims at:** a number that is what the server really holds.
  **For:** exact at the fd wall; scope 3's case becomes "a ceiling under 2,048 with a named reason", which a correct
  harness always passes.
  **Against:** a little more code in the client, and up to 60 s of waiting between runs.
- **B.** Keep the plan: last step held plus the `ESTABLISHED` count from `/proc/net/tcp`.
  **Aims at:** reusing `probe.sh connections`.
  **For:** already written.
  **Against:** overcounts by the accept queue, and the second runtime of scope 7 can get a false ceiling.

**Confidence:** A 90 % · B 10 %

**Recommendation:** A, because the max connections is the headline of the table and of prediction 7.

**Flips if:** nothing realistic.

### [run, conformance] : How does the conformance prove a partial write?

The planned case (the client reads 1 KiB at a time) never makes the server's write partial: loopback buffers
autotune to megabytes, a `/posts/:id` response is under 1 KiB, and PHP streams can't shrink `SO_RCVBUF`. So scope 6
can go green while DIY's partial-write path never runs.

**Question:** what case forces DIY to keep the rest of a response and wait for the socket to be writable?

- **A.** End to end: pipeline enough requests in one write that the responses exceed the loopback buffers (several
  MB), read nothing for 200 ms, then read everything and check each response, in order.
  **Aims at:** one case that tests all three runtimes the same way.
  **For:** no special code in DIY.
  **Against:** fragile: the client's own big write can block while the server applies back-pressure, and Swoole may
  close on its output buffer limit, a setting rather than a bug.
- **B.** A DIY test at the connection level, run by `check.sh`: a `stream_socket_pair` (Unix socket, about 200 KiB of
  buffer) whose peer doesn't read, a response larger than that, then the peer reads and the bytes must arrive whole
  and in order.
  **Aims at:** same goal, deterministic, where the risk is (DIY's own write code).
  **For:** small buffers on demand, no timing, no sizing guess.
  **Against:** DIY's connection code must accept any stream (it's ext-event, so it can); Swoole and Workerman aren't
  tested on this (they are mature).
- **C.** Drop the case from the Done-when.
  **Aims at:** less work.
  **For:** k6 reads promptly, so the bench rarely hits a partial write.
  **Against:** a slow client in the real run would hit an untested path.

**Confidence:** A 30 % · B 65 % · C 5 %

**Recommendation:** B, because it puts correctness first with a test that can't pass by accident, on the only server
whose write path is new code.

**Flips if:** DIY's connection code can't be driven on a socket pair without a second code path (then A, sized by
trial).
