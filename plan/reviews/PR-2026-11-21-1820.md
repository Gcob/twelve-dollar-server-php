## Description de la PR

**Résumé**

Le labo de la phase 3 et sa première comparaison de runtimes : un handler commun, trois serveurs (Swoole, Workerman avec ses 5 caches de requêtes retirés ou non, et un serveur maison sur ext-event), un test de conformité HTTP, un test de connexions inactives, et les résultats mesurés avec leur lecture. Avec le même handler, sur arm64 (Docker Desktop, M3 Pro), le serveur maison coûte le moins par requête et Workerman patché est à 3 % de Swoole.

```diff
 lab/
+  servers/handler.php              le même handler pour les trois
+  servers/bake-swoole.php
+  servers/bake-workerman.php       WORKERMAN_TREE=nocache|stock
+  servers/bake-diy.php             boucle ext-event et parseur HTTP maison
+  conformance.sh                   HTTP/1.1 en sockets bruts
+  conns.sh                         connexions inactives, max et mémoire par connexion
+  images/install-extras.sh         pcntl, sockets, event, deux arbres Workerman
~  macro.sh                         --ext, --env, --label, mémoire sous charge, other_containers
~  check.sh                         vérifications dont shellcheck épinglé
+  results/2026-11-21-bake-off/     README, summarize.sh, JSON de chaque run
```

**Décisions**

- **PHP 8.5, ext-event pour Workerman et le serveur maison :** `stream_select` plafonne à 1,024 descripteurs, ce qui fausserait le test de connexions; même boucle pour les deux, donc seule la couche HTTP diffère.
- **Chaque runtime garde ses propres en-têtes de réponse :** moins d'octets d'en-tête fait partie de ce qu'un runtime peut gagner; les résultats donnent les octets exacts.
- **Backlog 4,096 et `TCP_NODELAY` pour les trois :** le défaut de PHP (32) classerait le harnais, pas le runtime.
- **Le max de connexions est compté par le client :** les connexions qui ont eu leur réponse et sont encore ouvertes; une erreur côté client fait échouer le run au lieu de passer pour un plafond.
- **L'écriture partielle du serveur maison est testée sur une paire de sockets :** sur loopback, les tampons grossissent jusqu'à des mégaoctets, donc un test de bout en bout peut passer sans jamais écrire en partie.
- **Les VUs de k6 sont à taux / 5 pour toute la série :** à taux / 10, des arrêts de 100 à 300 ms ont fait perdre des itérations sur `posts.js`; le premier essai est gardé dans `first-try-700-vus/` et n'est compté nulle part. La cause des arrêts n'est pas séparée (hôte ou lecture de la base).
- **Seuls les runs valides sans autre conteneur comptent :** un run invalide est refait une fois en fin de tour; les deux restent visibles dans le README.

**Ce qu'on a appris**

- Workerman garde une connexion HTTP 60 s quoi que disent `Connection: close` ou l'en-tête de réponse : un client qui lit jusqu'à la fermeture attend une minute.
- Un `Response` de Workerman n'ajoute pas d'en-tête `Server`.
- `fread` sur un socket PHP rend au plus 8 192 octets, quelle que soit la longueur demandée; un test qui appelle `onReadable()` une fois par écriture doit boucler.
- La plage de ports éphémères de la VM est 55000-65535 (10 536 ports), pas celle par défaut de Linux : 66k connexions demandent 7 adresses source.
- La mémoire de Swoole n'est pas linéaire en connexions (69 KiB chacune sous 10,000, 5 KiB au-delà de 20,000) : une pente unique la cache.
